# 关系数据库与规范发布架构（V2.1 提案）

> 本仓库是长期维护的规范数据源，而不是VezroCAD的生产项目数据库。SQL：`schema/standard-management-v2.1.sql`。

## 推荐方案：Git版本库 + SQLite管理草稿 + 不可变规范快照

- **GitHub / 本仓库**：审核后的JSON、图层目录、规则、线宽、色彩映射、版本与ADR，是已发布规范的权威来源。
- **SQLite本地管理库**：按对象/专业/图纸/视图建立外键与多对多关系，支持可视化编辑、关系查询、草稿、审计与差异对比。管理库不与插件实时强绑定。
- **版本化规范包**：由管理器导出JSON，CI检查后通过PR审核并固定发布；插件在离线情况下从本地缓存读取，记录所用版本与摘要以便排查。
- **DWG智能构件真实数据**：墙体位置、门洞、柜体参数仍归CAD工程对象所有；SQLite可以有可重建的索引或工程关系缓存，不能代替DWG实际几何及可编辑身份。
- **未来多人协作**：可将管理页面服务化，但不改变CAD本地规范快照消费模式。没有理由因为远端服务断网导致用户不能画施工图。

## 关系表及其价值

`standard_revision`（草稿/审核/已发布）是每条规范规则的所属版本。

| 核心关系 | 典型表 |
|---|---|
| 专业 → 图纸类型 → 基础视图 | `profession`, `sheet_type`, `view_preset` |
| 图纸类型 ↔ 语义对象标签 ↔ 显示动作 | `sheet_expression`, `semantic_tag` |
| 业务语义 ↔ 表达角色 ↔ 图层 | `role_layer_binding`, `representation_role`, `layer_rule` |
| 图纸类型 ↔ 可选比例规则 | `sheet_scale_binding`, `scale_policy` |
| 纸张模板 + 线宽预设 | `paper_template`, `lineweight_profile`, `lineweight_by_role` |
| 输出模式 ↔ STB稳定样式名 ↔ 颜色 | `print_mode`, `plot_style`, `plot_style_color` |
| 表达层级关系 | `draw_order_constraint` |
| 修改留痕 | `change_audit` |

实际表结构设复合外键 `(revision_id,stable_id)` 防止把V2.0角色关联到V2.1的图层。复杂可选条件使用受Schema校验的JSON字段，而不是让每一项都拆成几十张零散子表。

### 规范维护生命周期

克隆已发布规范 → 在SQLite生成新的DRAFT版本 → 管理页面编辑并执行外键/规则图/线宽/样式完整性检查 → 生成JSON规范快照和差异PR → GitHub评审 → CI + AutoCAD测试 → 发布固定版本 → 插件选择或回滚到指定版本。

**必须保证单一权威来源：** SQLite是编辑工作区、不能单独发布与生产生效；Git上已审核发布的快照是正式数据。禁止插件边画图边自动写回Git或把Git与SQLite视作两个随意双写的数据源。

## 客户数据与工程关系

客户端未来可拥有单独的 `project-index.sqlite`，记录项目UID、图纸实例、构件UUID到图纸影响关系等 **可重建的索引**。项目图纸必须有独立保存/复制/迁移策略，不应只凭DWG Handle做跨文件稳定标识；需要项目UID + 构件稳定ID和克隆冲突处理。

这一工程索引与标准库应分开，客户地址、真实施工图、内部商业模板不可直接放进当前公开的规范仓库。即使只保存表结构，生产数据库也不应误上传。

## 对AutoCAD 2027的落地建议

优先 C#/.NET + `Microsoft.Data.Sqlite`（或确有需求时用EF Core migrations）+ WebView2 React/TypeScript 管理UI。插件通过 `IStandardCatalogProvider` 等接口读取发布快照，不要求G1立即开发SQL层。
